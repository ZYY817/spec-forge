# 评测场景

用以下场景检查 Skill 是否真的按设计工作。评测时关注输出行为，不要只检查文档格式。

## 场景 1：一句话小需求

输入：给列表页加一个导出按钮。

期望：不追问过多，不生成大型 PRD；输出简短背景、功能说明和关键验收，并标出真正必要的待确认项。

## 场景 2：带截图的方案讨论

输入：用户提供聊天背景和页面截图，并说“这里加个提示”。

期望：先理解页面和数据关系，讨论提示是否能解决根本问题；用户未要求写单前，不直接生成正式需求。

## 场景 3：复制或关联逻辑

输入：复制对象后生成新对象，但详情配置仍关联旧对象。

期望：写清原对象、新对象、关联位置、替换规则、其他配置是否沿用和异常处理；必要时使用映射表或前后示意。

## 场景 4：用户中途改变结论

输入：先讨论短期提示和长期映射，用户最后决定只保留长期映射。

期望：最终文档删除短期方案，不把旧方案写成当前需求，也不把已确认结论写成待确认。

## 场景 5：AI Coding 需求

输入：用户希望从零实现一个功能或产品。

期望：先写业务需求；只有在目标明确后，再补充项目分析、技术选型、模块拆分、分阶段实现、测试和交付要求。不能脱离项目上下文强行指定框架。

## 场景 6：已有需求变更

输入：用户提供旧需求，并说明“只改复制后的关联逻辑，原来的数量和标签不变”。

期望：识别变更和不变内容，写清影响范围，不重复改写无关部分，也不把原逻辑全部推倒重来。

## 场景 7：图片和多种输出对象

输入：用户提供列表页、确认弹窗和详情页截图，并说明要给开发排期。

期望：分别识别截图事实和推断，写清页面路径和视觉位置；使用最少但足够的图示；输出工作需求单，不主动生成 Word 或完整技术设计。

## 场景 8：需求实现对照

输入：用户提供需求单和已实现页面，要求确认是否完成。

期望：逐项对照需求、实现和验证证据，标记已完成、部分完成、未完成和偏差，不用“看起来完成”替代验证。

## 失败信号

- 一收到背景就输出完整需求单。
- 强制使用固定章节、编号或复杂术语。
- 把用户的一句话方案当成最终方案。
- 只写“增加映射”却没写映射对象和替换位置。
- 用大量通用异常和非功能需求填充篇幅。
- 把长期方向误写成本次必须交付。
- AI Coding 部分压过了用户真正需要的工作需求。
